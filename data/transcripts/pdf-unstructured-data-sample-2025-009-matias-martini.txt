Event storming session — we try to follow, as it is event driven architecture, a lot of distributed
transactions, in this particular way it makes sense to make an event architecture, as every event has
an output. Async communication. We receive a message, if you don’t have an event driven
architecture, you will be less efficient.
Domain driven design vs domain oriented arquitecture — separate your business logic in domains
and make the implementation of that model. A way in which you model your business through the
code.
Event driven is when the business is async — because the nature of our business is async as we
have a lot of processing time. You may want to have asynchronous communication. We are doing that
task and we will let you know when the task is finished. A solution for a real problem, your domain, is
compatible with this strategy.
When the user wants to generate a stage of an account or a report, I don’t want the user to keep
working when the process is finished, I will say that I will let you know when the process is done. If it is
something that is back office.
When I have to request transactions to the bank API, in that moment the transactions can take up to
15 minutes, if the user wants to move money we will need a confirmation that the money is moved, in
that case we will process the order, and we will let the user through an email or notification. When
something takes time and you don’t want the user to wait or experience delay we use event driven.
Delivery use case — for example in Rappi, I want to have an order, we are processing your order and
we will let you know when is ready. I have the delivery in my power, there is a service that takes the
order and update it and let the user know.
Payments and rewards case — I would use an asynchronous approach, if they recycle, if the service
sends a message to the distributor, wait for the answer to the message and update the database.
Send a push notification to the user. It depends on the scale of the application.
